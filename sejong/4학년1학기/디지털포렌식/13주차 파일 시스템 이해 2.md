# 1. FAT 파일시스템 생성
## 1.1 FAT 파일시스템 내부 구조
![[Pasted image 20260613183415.png]]
```text
Boot Sector → Reserved Sector → FAT1/FAT2 → Root Directory → Data Area
```
### 1.1.1 주요 영역
| 영역                   | 핵심                                                      |
| -------------------- | ------------------------------------------------------- |
| **Boot Sector**      | 파일시스템 시작 영역. `BPB`와 `Boot Code` 포함                      |
| **BPB**              | 섹터 크기, 클러스터 크기, FAT 위치, **Root Directory** 위치 등 레이아웃 정보 |
| **Reserved Sectors** | **Boot Sector** 이후부터 FAT 시작 전까지의 예약 공간                  |
| **FAT1**             | 메인 FAT. 클러스터 상태와 다음 클러스터 연결 정보 저장                       |
| **FAT2**             | **FAT1** 손상 시 복구를 위한 백업 FAT                             |
| **Root Directory**   | 파일/하위 디렉터리의 **Directory Entry** 저장                      |
| **Data Area**        | 실제 폴더/파일 데이터가 클러스터 단위로 저장되는 영역                          |
### 1.1.2 FAT Entry 값
| **FAT Entry** 값 | 의미 |
| --- | --- |
| `0x00000000` | 비어 있는 클러스터 |
| 다음 클러스터 번호 | 현재 클러스터 다음에 읽을 클러스터 |
| `0x0FFFFFFF` | 파일의 끝, EOF |
### 1.1.3 Directory Entry
| 항목              | 내용                                                   |
| --------------- | ---------------------------------------------------- |
| 크기              | 기본 **Directory Entry**는 32B                              |
| 저장 정보           | 파일명, 확장자, 속성, 생성/수정 시간, 시작 클러스터, 파일 크기               |
| **Short File Name** | 8.3 규칙, 파일명 8자 + 확장자 3자                              |
| **Long File Name**  | **LFN**, 8.3 한계 보완, 유니코드 2B 문자 사용, 여러 **Directory Entry** 사용 |
| 엔트리 구분          | `Attribute = 0x0F` **LFN**, `Attribute = 0x20` 일반 파일     |
## 1.2 FAT 파일 생성 과정
![[Pasted image 20260613184148.png]]
예시 조건:
- 클러스터 크기: 4096B
- 파일명: `file1.dat`
- 파일 크기: 6000B
- 필요한 클러스터 수: 2개
### 1.2.1 생성 흐름
1. `dir1` 안에 파일 생성 요청이 발생한다.
2. **Directory Entry**에서 새 파일 정보를 기록할 자리를 찾는다.
3. FAT에서 비어 있는 **FAT Entry** `0x00`을 검색한다.
4. 첫 클러스터로 190번을 확보하고 4096B를 저장한다.
5. 남은 1904B 저장을 위해 191번 클러스터를 추가 할당한다.
6. **Directory Entry**에 시작 클러스터 190과 파일 크기 등을 기록한다.
### 1.2.2 Directory Entry와 FAT Entry의 `0x00`
| 위치 | `0x00` 의미 |
| --- | --- |
| **Directory Entry** 첫 바이트 | 새 엔트리 시작/이후 엔트리 없음 |
| **FAT Entry** | 비어 있는 클러스터, 즉 새 데이터 저장 가능 |
삭제된 **Directory Entry**는 첫 바이트가 `0xE5`로 표시되며, 새 파일 엔트리로 재사용될 수 있다.
### 1.2.3 FAT 테이블 작성
```text
FAT[190] = 191
FAT[191] = 0x0FFFFFFF
```

| 항목 | 의미 |
| --- | --- |
| `FAT[190] = 191` | 190번 클러스터 다음은 191번 클러스터 |
| `FAT[191] = 0x0FFFFFFF` | 191번 클러스터가 파일의 끝 |
### 1.2.4 슬랙
- 사용 클러스터: 190번, 191번
- **RAM Slack**: 144B
- **File Slack**: 2048B
# 2. FAT 파일 삭제
![[Pasted image 20260613184157.png]]
## 2.1 삭제 시 변경되는 영역
| 영역 | 삭제 시 변화 | 복구 단서 |
| --- | --- | --- |
| **FAT Entry** | 파일이 사용하던 클러스터 엔트리를 `0x00`으로 초기화 | 연결 정보는 사라지지만 연속 저장 파일은 복구 가능 |
| **Directory Entry** | 파일 이름 첫 글자를 `0xE5`로 변경 | 파일 크기, 시간, 속성, 시작 클러스터가 남을 수 있음 |
| **Data Area** | 파일 데이터 자체는 즉시 삭제되지 않음 | 덮어쓰기 전까지 실제 파일 내용 확인 가능 |
핵심:
- **FAT 삭제**는 실제 데이터를 즉시 지우지 않고 인덱스 정보를 바꾼다.
- 포렌식 도구는 **Directory Entry**의 `0xE5` 값을 기준으로 삭제 파일 후보를 찾을 수 있다.
## 2.2 삭제 파일 복구 가능성
| 상황 | 복구 가능성 |
| --- | --- |
| **Directory Entry**에 파일 크기, 시간, 속성, 시작 클러스터가 남음 | 복구 단서 충분 |
| 파일이 연속 클러스터에 저장됨 | 시작 클러스터와 파일 크기만으로 복구 쉬움 |
| **Directory Entry** 또는 FAT 정보 손상 | **Data Area** 조각 분석 필요 |
| 파일이 조각난 상태 | 다음 클러스터 추정이 필요해 난이도 증가 |
| 삭제 후 같은 **Data Area** 클러스터에 덮어쓰기 발생 | 원본 복구 어려움 또는 불가능 |

# 4. NTFS 파일시스템
![[Pasted image 20260616225210.png]]
## 4.1 NTFS 등장 배경과 특징
| 구분     | 핵심                               |
| ------ | -------------------------------- |
| FAT 한계 | 조각화, 대용량 파일 처리 비효율, 안정성/보안 기능 부족 |
| 도입     | 1993년 Windows NT에서 최초 도입         |
| 현재 위치  | Windows OS의 주력 파일시스템             |
| 설계 방향  | 서버 환경을 고려한 안정성, 보안성 중심           |
### 4.1.1 NTFS 주요 기능
| 기능 | 의미 |
| --- | --- |
| **USN Journal** | 변경 기록 저장, 정전/강제 종료 시 롤백 단서 |
| **ADS** | `Alternate Data Stream`, 하나의 파일에 여러 데이터 스트림 저장 |
| **Sparse/압축** | 대부분 0인 데이터 저장 생략, 파일 압축 가능 |
| **EFS** | 파일 단위 암호화 |
| **BitLocker** 연계 | 볼륨 단위 암호화와 연계 가능 |
| **VSS** | Shadow Copy, 이전 버전 유지 |
## 4.2 NTFS 기본 구조
### 4.2.1 VBR
**VBR**(`Volume Boot Record`)은 부트 코드와 **BPB**를 포함한다.

| 바이트 offset, 10진수 | 바이트 offset, 16진수 | 설명                          |
| ---------------- | ---------------- | --------------------------- |
| 0 - 2            | 0x0000 - 0x0002  | Jump command to boot code   |
| 3 - 10           | 0x0003 - 0x000A  | OEM ID, `"NTFS"` 키워드        |
| 11 - 83          | 0x000B - 0x0053  | BIOS Parameter Block(**BPB**)   |
| 84 - 509         | 0x0054 - 0x01FD  | Boot code and Error Message |
| 510 - 511        | 0x01FE - 0x01FF  | Signature `0x55AA`          |
### 4.2.2 MFT
| 항목       | 핵심                                        |
| -------- | ----------------------------------------- |
| **MFT**      | `Master File Table`, 파일/디렉터리 메타데이터 관리의 핵심 |
| 0번 엔트리   | `$MFT` 자체 정보                              |
| 배치       | 엔트리가 디스크 전체에 흩어질 수 있음                     |
| FAT과의 대응 | FAT의 테이블 역할을 **MFT**가 수행                      |
### 4.2.3 MFT Entry 구성
| 구성        | 의미                                            |
| --------- | --------------------------------------------- |
| Header    | 엔트리 기본 정보                                     |
| Fixup     | 무결성 점검 및 복구 목적                                |
| **Attribute** | `STANDARD_INFORMATION`, `FILE_NAME`, `DATA` 등 |
## 4.3 NTFS 접근 및 생성 흐름
### 4.3.1 접근 흐름
```text
VBR → BPB에서 MFT 시작 위치 확인 → $MFT 접근 → $DATA로 구조 파악 → 파일/디렉터리 탐색
```
### 4.3.2 파일 생성 흐름
예시 조건:
- 파일명: `file1.dat`
- 파일 크기: 4000B
- 클러스터 크기: 2048B
- 필요한 클러스터 수: 2개
```text
VBR 확인 → $MFT의 $BITMAP에서 미사용 엔트리 탐색
→ MFT 엔트리 초기화 → FILE_NAME/크기 등 속성 기록
→ 빈 클러스터 배정 → 디렉터리 인덱스 엔트리 생성
→ $LogFile, $UsnJrnl에 변경 기록
```
## 4.4 삭제 복구와 파일 카빙
### 4.4.1 NTFS 삭제 복구 핵심
| 항목        | 의미                                     |
| --------- | -------------------------------------- |
| 공통 원리     | FAT처럼 데이터는 남고 인덱스/관리 정보가 변경됨           |
| `$BITMAP` | 비사용 영역 분석                              |
| **MFT** 엔트리   | `FILE_NAME`, 파일 크기, 데이터 위치 정보를 이용해 재획득 |
| 메타데이터 부족  | 비할당 클러스터 분석 필요                         |
| FAT과 차이   | FAT은 **FAT Entry** 중심, **NTFS**는 **MFT** 중심        |
### 4.4.2 포렌식 분석 기법
| 기법 | 핵심 |
| --- | --- |
| 슬랙 공간 분석 | 파일 슬랙, 파일시스템 슬랙, 볼륨 슬랙 분석 |
| **파일 카빙** | 메타데이터 없이 파일 **시그니처** 기반으로 복구 |
| **시그니처** | 보통 Header와 Footer를 의미 |
| 활용 예 | JPG, GIF 등 고유 패턴 기반 복원 |
