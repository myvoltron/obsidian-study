# 1. 문자의 저장 및 처리
## 1.1 BASE64 Encoding
### 1.1.1 Base64의 개념
- 바이너리 데이터를 문자 데이터로 안전하게 변환하는 **인코딩** 방식이다.
- URL, HTTP 요청, 검색 쿼리처럼 특수문자나 공백이 문제가 될 수 있는 환경에서 사용된다.

### 1.1.2 인코딩과 디코딩
| 구분  | 내용                             |
| --- | ------------------------------ |
| **인코딩** | 원본 바이너리 데이터를 **Base64** 문자 집합으로 변환 |
| **디코딩** | **Base64** 문자열을 원본 바이너리 데이터로 복원    |
| 핵심  | 전송 중 깨지기 쉬운 데이터를 안전한 문자 형태로 바꿈 |
### 1.1.3 Base64 인코딩 방식
**Base64**는 원본 데이터를 3바이트씩 끊어 4개의 문자로 바꾸는 방식이다.
```text
3Byte = 24bit
24bit = 6bit + 6bit + 6bit + 6bit
6bit 값 하나 = Base64 문자 하나
```
- 6bit는 `0~63`까지 총 64개 값을 표현할 수 있다.
- 이 64개 값이 `A-Z`, `a-z`, `0-9`, `+`, `/` 같은 문자에 매핑된다.
- 바이너리 데이터가 문자 형태로 바뀌기 때문에 텍스트 기반 환경에서 안전하게 전송할 수 있다.
- 단, 3바이트가 4문자로 바뀌므로 **인코딩** 결과의 크기는 원본의 약 `4/3배`가 된다.
### 1.1.4 Base64 인코딩 예시
문자열 `Man`을 예로 들면 다음과 같다.
```text
M      a      n
77     97     110        ASCII 10진수
01001101 01100001 01101110
```
24bit를 6bit씩 나누면 다음과 같다.
```text
010011 010110 000101 101110
19     22     5      46
```
각 값을 **Base64** 문자표에 매핑하면 다음 결과가 나온다.
```text
19 = T
22 = W
5  = F
46 = u
```
따라서 `Man`의 **Base64** **인코딩** 결과는 다음과 같다.
```text
Man → TWFu
```
### 1.1.5 패딩
입력 데이터 길이가 3바이트 단위로 딱 맞지 않으면 **Base64** 결과 끝에 "=" 문자를 붙여 4문자 단위가 되도록 맞춘다.

| 원본    | **Base64** 결과 | 의미              |
| ----- | --------- | --------------- |
| `Man` | `TWFu`    | 3바이트라 **패딩** 없음     |
| `Ma`  | `TWE=`    | 2바이트라 `=` 1개 추가 |
| `M`   | `TQ==`    | 1바이트라 `=` 2개 추가 |
### 1.1.6 Base64 디코딩 방식
**디코딩**은 **인코딩**의 반대 과정이다.
```text
Base64 문자 → 6bit 값 → 8bit 단위로 재조립 → 원본 바이너리
```
- "=" **패딩**은 원본 데이터 길이를 맞추기 위한 표시이므로 복원 과정에서 제거된다.
- **Base64**는 암호화가 아니라 **인코딩**이므로 누구나 **디코딩**할 수 있다.
- 포렌식에서는 로그, 웹 요청, 이메일, 파일 내부 문자열에서 **Base64**처럼 보이는 값을 찾아 원본 데이터를 복원하는 데 활용할 수 있다.
## 1.2 Character Code
### 1.2.1 문자 코드의 역할
- 문자를 컴퓨터가 저장할 수 있는 숫자와 비트 패턴으로 매핑하는 표준이다.
- **문자 코드**가 다르면 같은 바이트열도 다른 문자로 해석될 수 있다.
- 표준화된 **문자 코드**가 있어야 컴퓨터 간 데이터 전송, 복사, 로딩 시 같은 문자를 같은 방식으로 표시할 수 있다.
### 1.2.2 주요 문자 코드
| 구분 | 특징 |
| --- | --- |
| **ASCII** | 영문 중심 7비트 문자 체계, 128개 기호 표현. 알파벳, 숫자, 특수문자, 제어문자 포함 |
| **Extended ASCII** | 8비트로 확장하여 256개 기호 표현 |
| **Unicode** | 전 세계 문자를 통합적으로 표현하기 위한 표준 |
| **UTF-8** | 1~4바이트 가변 길이 방식, 현대 시스템에서 널리 사용 |
| **UTF-32** | 4바이트 고정 길이 방식 |

### 1.2.3 Unicode 세부 개념
| 구분 | 의미 |
| --- | --- |
| **Unicode Point** | 각 문자에 부여된 고유한 16진수 번호 |
| **UCS** | Universal Character Set, 전 세계 문자를 표현하기 위한 문자 집합 |
| **BMP** | Basic Multilingual Plane, 대부분의 기본 문자가 포함되는 유니코드 영역 |
| **UCS-2** | 2바이트 고정 길이 방식, **BMP** 영역 문자 표현 |
| **UCS-4** | 4바이트 고정 길이 방식, 모든 유니코드 문자 표현 가능 |
| **UTF-8** | 1~4바이트 가변 길이 방식, **ASCII**와 호환성이 좋아 현대 시스템에서 널리 사용 |
| **UTF-32** | **UCS-4**와 유사한 4바이트 고정 길이 **인코딩** |

- **Unicode**는 문자에 번호를 부여한 표준이고, **UTF-8**/**UTF-32**는 그 번호를 실제 바이트로 저장하는 **인코딩** 방식이다.
- 같은 **Unicode** 문자라도 어떤 **인코딩**을 쓰는지에 따라 실제 바이트열은 달라질 수 있다.
## 1.3 한글 문자 코드
### 1.3.1 한글 문자의 특징
- 한글은 초성, 중성, 종성을 조합해 글자를 만든다.
- 조합 방식에 따라 글자 모양이 달라지고 경우의 수가 많다.
- 알파벳보다 폰트 제작과 **인코딩** 방식이 복잡하다.

### 1.3.2 한글 인코딩 방식
| 방식 | 특징 | 한계 / 활용 |
| --- | --- | --- |
| **조합형** | 초성·중성·종성을 조합해 글자 생성 | 모든 조합 표현은 가능하지만 모양 품질이 낮음 |
| **완성형** | 자주 쓰는 글자를 완성된 형태로 저장 | 정의되지 않은 글자는 표현 어려움 |
| **확장 완성형** / **EUC-KR** | **완성형**의 부족한 글자를 보완한 2바이트 계열 | 국내 환경에서 많이 사용 |
| **Unicode** / **UTF-8** | 다양한 언어와 한글을 함께 표현 | 현대 시스템의 기본 선택지 |
# 2. 시간 정보 표현
## 2.1 시간 정보의 의미
### 2.1.1 포렌식에서의 시간
- 생성, 수정, 접근, 실행 시각은 사건 타임라인 복원의 핵심 단서이다.
- 시스템 시간이 실제 시간과 다를 수 있으므로 PC 설정 시각과 KST/UTC 기준을 함께 확인해야 한다.
### 2.1.2 시간 기준
| 기준  | 내용                          |
| --- | --------------------------- |
| GMT | 경도 0도를 기준으로 한 평균 태양시        |
| UTC | 1972년부터 쓰인 국제 표준시, 원자 시계 기반 |
| KST | UTC+9, 한국 표준시               |
## 2.2 파일 시스템의 시간 저장 방식
### 2.2.1 주요 포맷
| 파일 시스템 | 시간 저장 방식         | 특징                 |
| ------ | ---------------- | ------------------ |
| FAT    | **MS-DOS Date/Time** | 4바이트 구조, 2초 단위 정밀도 |
| NTFS   | **FILETIME**         | 8바이트 구조, 100나노초 단위 |
### 2.2.2 MS-DOS Date/Time
**MS-DOS Date/Time**은 날짜와 시간을 각각 16bit씩 나누어 저장한다.
```text
Date 2Byte + Time 2Byte = 총 4Byte
```

| 필드  | 비트 수 | 해석       |
| --- | ---- | -------- |
| 연도  | 7bit | 1980 + 값 |
| 월   | 4bit | 1~12     |
| 일   | 5bit | 1~31     |
| 시   | 5bit | 0~23     |
| 분   | 6bit | 0~59     |
| 초   | 5bit | 2초 단위    |
- 표현 가능한 범위는 1980년부터 2107년 12월 31일까지이다.
- 초는 2초 단위로 기록되므로 시간 정밀도가 낮다.
- 제한된 공간에 압축 저장하므로 정교한 포렌식 타임라인 분석에는 한계가 있다.
### 2.2.3 Endian과 시간 해석
- Intel 계열 시스템은 **Little-Endian**을 사용하므로 바이트 순서를 뒤집어 해석해야 하는 경우가 많다.
- 예를 들어 `A472723B`가 **MS-DOS Date/Time** 값이라면 저장 순서와 포맷 규칙을 먼저 확인한 뒤 날짜와 시간 필드로 분리한다.
```text
저장 값: A4 72 72 3B
Little-Endian 해석: 3B 72 72 A4
```
- 시간 값은 단순히 16진수를 10진수로 바꾸는 것이 아니라, **Endian**과 필드 비트 구조를 함께 고려해 해석해야 한다.
### 2.2.4 FILETIME
- NTFS에서 사용하는 시간 포맷이다.
- 1601년 1월 1일 00:00:00 UTC를 기준으로 100나노초 단위를 누적해 저장한다.
- **MS-DOS Date/Time**보다 표현 범위와 정밀도가 높다.
# 3. 파일 시그니처 분석
## 3.1 파일 시그니처의 의미
### 3.1.1 개념
- 파일 내부에 기록된 고유 패턴으로 파일의 실제 종류를 식별하는 단서이다.
- 확장자는 쉽게 바꿀 수 있으므로 파일 종류 판단은 내부 구조와 시그니처를 기준으로 해야 한다.
- 확장자는 운영체제가 어떤 프로그램으로 파일을 열지 결정하는 표시일 뿐 파일의 실제 종류를 보장하지 않는다.
- 악의적 사용자는 확장자를 변경해 파일을 위장할 수 있다.
### 3.1.2 파일 포맷 구조

| 영역       | 내용                             |
| -------- | ------------------------------ |
| **Header**   | 파일 종류 식별용 시그니처, 크기, 메타데이터 위치 등 |
| **Metadata** | 파일 설명 정보, 생성 도구, 시간 정보 등. 파일 형식에 따라 없을 수도 있음 |
| **Body**     | 실제 데이터 내용                      |
### 3.1.3 포렌식 활용
- 확장자를 위장한 파일을 식별한다.
- 파일 손상 또는 삭제 후 복구 가능성을 판단한다.
- **파일 카빙** 시 시작·종료 패턴을 찾는 기준으로 사용한다.
